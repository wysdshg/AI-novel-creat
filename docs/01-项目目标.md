# 01 · 项目目标与预期效果

> 本文是项目的**唯一目标定义**。任何需求争议以本文为准。  
> 最后更新：2026-09-09



---

## 1. 这是什么

一个**本机单人使用的长篇小说写作辅助工具**（B/S 架构，浏览器访问）。

不是产品，不是 SaaS，不给第二个人用。所有设计决策以"作者本人写得更快、更稳、不崩"为唯一判据。

---

## 2. 使用者与场景

- **使用者**：一个人（作者本人）
- **硬件**：本机，RTX 4060 Laptop 8GB，本地 Ollama（qwen3.5:4b）+ 云端模型（**ModelScope Qwen/Qwen3.8-Flash-Next【当前默认，2026-09-09 换】** / NVIDIA GLM-5.2 / SiliconFlow Qwen3-8B）
- **检索模型选型（2026-09-09 定，供检索升级用）**：Embedding = 硅基流动 **BAAI/bge-m3**；重排 = 硅基流动 **BAAI/bge-reranker-v2-m3**。均为免费档。

### 题材：**题材无关**（重要）

工具必须能适配**多种题材**，不是某一本书的定制器。
- 架空王朝（宋式小盛世基调，文武平等）探案/官场向 —— **仅为当前测试题材**，不是目标
- 凡是与"某一种题材"强绑定的设计（写死的模板、固定境界体系、特定官职链），都是**待改造项**
- 题材差异应通过「设定库 + 参考文档 + SKILL」承载，而不是硬编码进代码

## 3. 核心命题：AI 该接管什么

**判据：AI 只接管"人做不到"的事，不接管"人不愿意做的苦力"。**

| 交给 AI（人做不到）                     | 留给作者（人是强项）     |
| ------------------------------- | -------------- |
| 跨几十章的**一致性**（人设不崩、设定不自相矛盾）      | 故事结构与大纲        |
| 跨几十章的**伏笔追踪**（埋了没、收了没、哪条烂尾）     | 文风与审美判断        |
| 长篇**上下文压缩**（写到第 80 章还记得前面发生了什么） | 情节创意与走向选择      |
| **设定校验**（写的内容是否违反已定规则）          | 是否采纳 AI 的每一个建议 |
| 写后**自动沉淀**（记忆/摘要/大事记/新实体）       | 最终成稿的所有文字      |

### ⚠️ 关于套路模板（2026-09-09 修正）

**上一版写"套路模板价值最低、列为删除对象"，这个判断是错的，已推翻。**

- **流水线小说（网文量产）恰恰最需要套路模板**——这是它的生产工具，不是可选项。
- 目前的 7 条写死模板（秘境夺宝/宗门大比/穿越重生…）之所以看起来没价值，
  **不是因为模板没用，而是因为它是硬编码的、题材绑定的、且不能编辑**——与上文"题材无关"原则直接冲突。
- **正确方向**：模板应做成**可编辑、可新增、题材中立的结构化数据**（节奏骨架 / 情节节点 / 冲突类型 / 爽点分布），
  而不是一份写死的列表。
- **状态：实现方式待考究**（见 03）。当前不做删除，先冻结。

**修正后的判据**：不是"AI 别碰创意"，而是"**AI 提供结构与素材，作者掌握取舍**"。

## 4. 预期效果（成功标准）

一条主线闭环，跑通即算成功：

```
作者写/聊剧情 → AI 生成章节（流式，可中断）
              → 写后自动沉淀（记忆/摘要/大事记/新实体/伏笔）
              → 下一章自动带上前情、设定、伏笔
              → 作者随时查"埋了哪些伏笔没收""前面发生过什么"
```

**可验收的四条硬指标**：

1. **不崩**：写到第 50 章时，AI 仍准确知道前 49 章发生了什么（靠记忆层，不靠硬塞全文）
2. **不飘**：生成的正文不违反已录入的设定（靠设定校验，不是靠祈祷）
3. **不漏**：埋下的伏笔能被追踪到回收或标记为烂尾
4. **改得动**：改任何一处代码后，能在 5 分钟内确认没改坏（靠测试 + 日志 + 变更记录）

## 5. 明确不做（防止范围漂移）

| 不做            | 原因                                    |
| ------------- | ------------------------------------- |
| 多用户 / 登录 / 权限 | 单人本机工具                                |
| 云端部署 / 容器化    | 同上                                    |
| 移动端适配         | 作者只在桌前写作                              |
| 文风 LoRA 微调    | 成本远超收益，提示词工程已够用                       |
| ~~向量检索 / RAG~~ | **已撤销 → 改为「待优化」，见 §5.1**               |
| 协同编辑 / 版本分支   | 单人写作不需要                               |
| 100% 测试覆盖率    | 只测容易崩的地方（见 06）                        |

### 5.1 检索能力：待优化（2026-09-09 修订）

**现状**：目录 + 关键词（2-gram）+ 按需加载（`LOAD_REFS` / `LOAD_SETTING`）。
**能用**，但召回有天花板——依赖字面匹配，抓不住语义相关。

**升级方向（已定，未实施）**：

| 项      | 说明                                             |
| ------ | ---------------------------------------------- |
| Embedding | **硅基流动 BAAI/bge-m3**（免费档，2026-09-09 选定）    |
| 重排 Rerank | **硅基流动 BAAI/bge-reranker-v2-m3**（免费档，2026-09-09 选定） |
| 存储     | 计划迁移到**向量库**                                    |
| 高级检索   | 部分场景（人物关系 / 事件因果 / 势力博弈）**GraphRAG 更合适**       |
| 检索策略   | **Hybrid 混合检索**（向量 + 关键词 + 图谱）                  |

> 状态：**待优化**。不阻塞其他整改，但**架构上要预留接口**，避免届时又是一次大改。
> 具体方案待单独设计：embedding 选型 / 向量库存哪 / chunk 策略 / 是否引入图数据库。

### 5.2 工作流：方案待定（2026-09-09）

**当前实现对效果不满意**，工作流"彻底该怎么做"尚未想清楚，暂列为**待定**。

已知的问题（不是 bug，是设计层面没想透）：

- 工作流生成的章节**不触发写后摄取**，与主链路行为不一致（双轨制）
- 3 个工作流、7 次运行——用得少，说明它没解决真实痛点
- 画布编辑器（771 行）+ DAG 引擎（800 行）投入不小，但产出价值不明

**在想清楚之前：不投入、不删除、不扩展。** 见 03 §3 战略待拍板。

## 7. 与"行业完整 Agent 流程"的差距（诚实记录）

按 12 环对照，本项目现状：

| 环节          | 状态                                                    |
| ----------- | ----------------------------------------------------- |
| 需求建模        | ✅ 本文                                                  |
| 知识 / 检索     | 🟡 **待优化**：目录+关键词可用但有天花板；计划 SiliconFlow 免费 embedding + 向量库 + GraphRAG + Hybrid（§5.1） |
| 工具调用        | 🟡 `LOAD_REFS` / `LOAD_SETTING` 自研行内协议，无 schema 校验无重试 |
| 编排          | ⚠️ DAG 引擎真实执行，但**效果不满意、方案待定**（§5.2）                  |
| 记忆          | ✅ **最强项**：章级 + 阶段 + 大事记 + 待确认实体                       |
| 生成          | ✅ SSE 流式 + 上下文预算裁剪                                    |
| **评估 eval** | ❌ 完全没有                                                |
| **观测**      | ⚠️ 有埋点无消费端，`trace_id` 无处可查                            |
| **反馈闭环**    | ❌ 用户改了什么不回流                                           |
| 安全护栏        | ❌ 无注入防护                                               |
| **工程基建**    | ❌ 零测试 / 零 logging / 无迁移工具                             |
| 成本治理        | ❌ 无 token 计量                                          |

**结论**：功能层可用，"让系统持续变好"的三环（评估 / 观测 / 反馈）全断。这是 03 中 Phase 3 的目标。
