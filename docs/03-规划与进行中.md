## 0. 为什么是切片式重写，不是全量重写

2026-09-09 已论证并拍板。核心理由（防止日后动摇）：

1. **架构没崩，崩的是工程纪律。** `router/service/core` 分层清晰、gateway 适配器模式正确、上下文引擎设计合理。缺的是测试/日志/变更记录——换仓库这些还是没有。
2. **全量重写有死亡谷**：写到 60–70% 时旧的不能忍、新的不能写稿，项目多半死在这段。
3. **硬踩过的坑会重踩**：04 里记的模型行为坑（思考字段厂商差异、重复惩罚逼崩采样…）是几十次调试换来的，重写等于清零。
4. **AI 结对特性**：AI 擅长"给定契约的单模块重写"，极不擅长跨全仓重构。切片是顺应为之。

**切片式重写的含义**：每个模块**内部允许 100% 推倒重写**，但必须一次一个、接口契约不动、写完有测试。

### 3.2 多 agent 协同方案（2026-09-09 决策：轻量版）

详见 `docs/07-任务分发手册.md`。

**最终决策（2026-09-09，推翻上一版"专用调度对话"方案）**：
- **主力单干为主**：默认所有活由主力 AI（WorkBuddy 写码）自己做
- **任务积压才分发**：只有"一下要改的任务多"时，主力 AI 拆出**可独立、文件不重叠**的子任务，生成「投递单」，用户复制粘贴给 TRAE / Zcode / OpenCode，当"邮差"
- **废弃**：专用调度 WorkBuddy 对话、任务卡文件系统、调度状态机（投递单 + 用户粘贴即可，零基建）

**为什么放弃现成编排框架**（已调研 Agent Orchestrator / AI-Coding-Tools-Collaborative / um-agent-orchestration 等）：它们都要求 agent 是**可被命令行 spawn 的 CLI**——四 agent 中只有 OpenCode 满足，WorkBuddy / TRAE / Zcode 均不可编程驱动。换血成 CLI agent 与用户免费额度策略冲突，不划算。

**保留不变的**：模型能力分级（🟢GLM-5.3-flash / 🟡deepseek-v4-flash·混元4 / 🔴轻量免费模型）、共享真相层（docs/02 + 06 + CHANGELOG 为唯一真相，agent 文档只记局部）、弱模型只接轻量外围活。

**何时重启框架调研**：① 开始并发投递（不等 A 回就发 B）② 多 agent 频繁改同一批文件 ③ 主力换成可 CLI 驱动 agent。三条件同时出现再说（届时看 Agent Orchestrator 类，支持 OpenCode + git worktree 隔离）。
